# 售后申请与工单处理

## 业务对象与状态

售后申请是用户针对本人订单中具体商品正式提交的退款、退货或换货请求。工单用于投诉、异常问题和人工跟进；工单不是申请。`tickets.after_sale_request_id` 可以关联同一用户的申请，数据库复合外键保证两者归属相同；申请本身通过订单及订单行复合外键保证商品归属。

| 对象 | 合法流转 | 说明 |
| --- | --- | --- |
| 售后申请 | `pending` → `approved` / `rejected` / `cancelled` | 用户可取消待审核申请；员工审核通过或驳回 |
| 售后申请 | `approved` → `processing` / `cancelled` | 退货、换货由员工开始处理；尚未开始处理时用户可取消 |
| 退款申请 | `approved` → `awaiting_external_refund` | 待外部支付系统执行退款；本项目没有支付接口，员工不能把退款申请标为 `completed` |
| 退货、换货申请 | `processing` → `completed` | 员工记录处理说明后结束 |
| 工单 | `open` → `in_progress` → `resolved` → `closed` | 员工接单、记录处理结果、结单；处理中也可直接关闭，但必须有处理说明 |

`approved` 只表示审核通过，`awaiting_external_refund` 只表示等待支付侧动作。这两个状态均不表示已退款，也不提供到账时间。退款实际支付、退款结果回调、到账核验及财务对账仍需外部系统实现；接入前不把退款申请置为已完成。

## 用户路径

用户页面 `/app/service` 通过 `GET /api/service/orders` 选本人订单，再用 `GET /api/service/orders/{order_no}/after-sale-preview?requestType=refund|return|exchange` 读取订单状态、商品行与当前有效的 `policies` 版本。用户填写原因、选择商品和政策，并明确勾选确认后向 `POST /api/service/after-sales` 发送：

```json
{
  "orderNo": "订单号",
  "orderItemId": "订单商品行 ID",
  "requestType": "refund",
  "reason": "商品故障",
  "policyReference": "预览返回的政策 ID",
  "submissionKey": "每次提交生成的幂等键",
  "confirmed": true,
  "sourceTicketNo": "可选的本人工单号"
}
```

写入服务端重新核验订单、商品、订单状态、政策有效期、确认与参数；没有有效政策时页面不允许提交。`sourceTicketNo` 可把既有本人工单转为与新申请关联的跟进工单；同一商品已有同类型开放申请时返回原申请并补齐关联，有其他类型开放申请时拒绝新提交。`GET /api/service/after-sales` 和 `GET /api/service/tickets` 只列本人记录；`POST /api/service/after-sales/{id}/cancel` 只允许本人取消 `pending` 或 `approved` 申请。对话中的 `query_after_sale`、`query_ticket` 仍可按公开编号或近期记录查询进度。

单商品订单的退款对话保持语义识别与服务端工具白名单：核对本人订单与商品、追问原因，再用 `query_refund_policy` 读取本人订单当前有效的商家退款政策；政策正文必须覆盖用户陈述的原因，助手才会给出固定确认文本，并把 `{stage: confirm, order_no, reason, policy_id}` 存到该条助手消息的 `workflow_state`。只有紧邻的助手消息保存了同订单、同原因、同政策 ID 的确认状态，且本轮用户原文正好是 `确认提交`，`submit_after_sale` 才创建 `pending` 申请，并把这个政策 ID 写入 `policy_reference`；写入层再校验该政策当前仍在生效区间。本人订单没有覆盖该原因的现行政策时不询问提交，改为陈述已核验的订单事实并引导本页面与人工审核，同时以 `refund_policy_unavailable` 记入低置信度问题池；知识库检索结果只是说明材料，不能作为提交依据。多商品订单引导到页面选择具体商品。首次说“我要退款”不直接写入；用户拒绝也不写入。投诉及无法直接办理的异常仍通过 `create_ticket` 登记工单。

## 员工路径

员工页面 `/staff/service` 分别列出售后申请和工单；对应 `GET /api/staff/service/after-sales`、`GET /api/staff/service/tickets`。申请列表展示订单商品快照以及提交时选用的政策正文或对话知识库引用内容，供人工复核。`POST /api/staff/service/after-sales/{id}/transition` 接收 `{ "status": "approved", "note": "..." }`；`POST /api/staff/service/tickets/{id}/transition` 接收 `{ "status": "in_progress", "note": "...", "afterSaleRequestId": "可选" }`。两个入口都使用员工 Cookie 权限，写入层锁定目标行并校验合法状态、处理人、关联申请归属及必要说明。申请分别记录审核人、推进人、结束人及审核/处理/结束时间；工单记录接手人、接手/解决/关闭时间及关闭人。

提交事务先锁用户行，靠 `(user_id, submission_key)` 唯一键和同订单商品、类型的开放申请检查实现幂等和并发去重。`ticket_no`、`request_no` 是各自独立的公开编号。mock 模式使用浏览器本地数据模拟页面流程，remote 模式只调用后端，不在错误时切换为 mock。

数据库结构只由新迁移 `0008_after_sale_ticket_flow` 扩展。定向测试 `backend/tests/test_service_workflow.py` 使用独立的 `aiden_service_flow_test` MySQL 库，运行前需提供 `backend/.env` 中的连接参数，并为同名测试库授予账号权限。
