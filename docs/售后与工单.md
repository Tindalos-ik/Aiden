# 售后申请与工单处理

## 业务对象与状态

售后申请是用户针对本人订单中具体商品正式提交的退款、退货或换货请求。工单用于投诉、异常问题和人工跟进；工单不是申请。`tickets.after_sale_request_id` 可以关联同一用户的申请，数据库复合外键保证两者归属相同；申请本身通过订单及订单行复合外键保证商品归属。

| 对象 | 合法流转 | 说明 |
| --- | --- | --- |
| 售后申请 | `pending` → `approved` / `rejected` / `cancelled` | 用户可取消待审核申请；员工审核通过或驳回 |
| 售后申请 | `approved` → `processing` / `cancelled` | 退货、换货由员工开始处理；尚未开始处理时用户可取消 |
| 退款申请 | `approved` → `awaiting_external_refund` | 待外部支付系统执行退款；本项目没有支付接口，员工不能把退款申请标为 `completed` |
| 退货、换货申请 | `processing` → `completed` | 员工记录处理说明后结束 |
| 工单 | `open` → `in_progress` → `resolved` → `closed` | 员工接单、记录处理结果、结单；处理中也可直接关闭，但必须有处理说明 |

`approved` 只表示审核通过，`awaiting_external_refund` 只表示等待支付侧动作。这两个状态均不表示已退款，也不提供到账时间。退款实际支付、退款结果回调、到账核验及财务对账仍需外部系统实现；接入前不把退款申请置为已完成。

## 用户路径

用户页面 `/app/service` 通过 `GET /api/service/orders` 选本人订单，再用 `GET /api/service/orders/{order_no}/after-sale-preview?requestType=refund|return|exchange` 读取订单状态、商品行与当前有效的 `policies`。每项政策返回 `id`、`name`、`version`、`content` 和 `snapshot`。`snapshot` 为服务端生成的 64 位小写 SHA256，绑定政策 ID、key、名称、版本、正文、启用状态和生效起止时间；页面不能自行改写快照。用户选择具体商品、填写或核对原因、选择政策，并明确勾选确认后向 `POST /api/service/after-sales` 发送：

```json
{
  "orderNo": "订单号",
  "orderItemId": "订单商品行 ID",
  "requestType": "refund",
  "reason": "商品故障",
  "policyReference": "预览返回的政策 ID",
  "policySnapshot": "所选预览政策的 snapshot（必填，64 位小写 SHA256）",
  "submissionKey": "每次提交生成的幂等键",
  "confirmed": true,
  "sourceTicketNo": "可选的本人工单号"
}
```

写入服务端重新核验订单、商品、订单状态、政策有效期、确认与参数，并锁定政策行核对 `policySnapshot`。同 ID 政策原地修改正文、版本或生效范围，以及停用或失效，都会拒绝旧快照，返回 HTTP 409，要求重新查询并确认。页面收到冲突后清空确认并重新加载政策预览；无有效政策时页面不允许正式提交，不能通过对话绕过此限制。`sourceTicketNo` 可把既有本人工单转为与新申请关联的跟进工单；同一商品已有同类型开放申请时返回原申请并补齐关联，有其他类型开放申请时拒绝新提交。相同幂等键重试仍返回已创建的原申请，不借重试创建新申请。`GET /api/service/after-sales` 和 `GET /api/service/tickets` 只列本人记录；`POST /api/service/after-sales/{id}/cancel` 只允许本人取消 `pending` 或 `approved` 申请。对话中的 `query_after_sale`、`query_ticket` 仍可按公开编号或近期记录查询进度。

单商品订单的退款对话保持语义识别与服务端工具白名单：核对本人订单与商品、追问原因，再用 `query_refund_policy` 读取当前有效的商家退款政策；政策正文必须覆盖用户陈述的原因，助手才会给出固定确认文本，并把 `{stage: confirm, order_no, reason, policy_id, policy_snapshot, request_type: refund}` 存到该条助手消息的 `workflow_state`。只有紧邻的助手消息保存了同订单、同原因、同政策 ID 与快照的确认状态，且本轮用户原文正好是 `确认提交`，`submit_after_sale` 才通过页面同用的 `submit_request` 创建 `pending` 申请。政策提交时变化则旧确认失效，仅保留订单与原因供重新核验；用户回复 `重新核验` 后重新查询本人订单及当前政策，核验通过再请求新的明确确认，不沿用旧确认。用户可以取消办理，不产生写入。

多商品退款、退货和换货不复制写入流程，先核验本人订单，再给出 Markdown 页面入口 `/app/service?orderNo=<编码后的已核验订单号>&requestType=refund|return|exchange`；已有逐字核验原因时附 `reason=<编码后的原因>`。页面仍自行向服务端重新核验，URL 参数不授予提交权限。下一步是选择具体商品、填写或核对原因、核对当前政策并确认提交；每个申请对应一条订单商品行。售后订单列表使用统一选择提示，跨轮订单选择保存申请类型和已核验原因；退款待确认时改为退货或换货，会清旧提交授权、重新核验订单并转页面。

本人订单没有覆盖原因的现行政策时不询问提交，陈述已核验订单事实，并提供带本人订单号及原因的退款页面链接用于选择商品、核对原因和政策；明确无有效政策时页面也不能正式提交。用户可以咨询政策或明确要求人工协助核对、审核，但这不表示售后申请已经创建或人工已经接入；同时以 `refund_policy_unavailable` 记入低置信度问题池。知识库检索结果只是说明材料，不能作为申请提交依据；已移除 `rag:` 引用写入授权与展示兼容路径。首次说“我要退款”不直接写入；用户拒绝也不写入。投诉及无法直接办理的异常仍通过 `create_ticket` 登记工单。

## 员工路径

员工页面 `/staff/service` 分别列出售后申请和工单；对应 `GET /api/staff/service/after-sales`、`GET /api/staff/service/tickets`。申请列表展示订单商品快照及关联商家政策的当前正文供人工复核；没有额外的政策正文历史快照表，不能把当前展示正文视作提交时的不可变归档。`POST /api/staff/service/after-sales/{id}/transition` 接收 `{ "status": "approved", "note": "..." }`；`POST /api/staff/service/tickets/{id}/transition` 接收 `{ "status": "in_progress", "note": "...", "afterSaleRequestId": "可选" }`。两个入口都使用员工 Cookie 权限，写入层锁定目标行并校验合法状态、处理人、关联申请归属及必要说明。申请分别记录审核人、推进人、结束人及审核/处理/结束时间；工单记录接手人、接手/解决/关闭时间及关闭人。

提交事务先锁用户行，靠 `(user_id, submission_key)` 唯一键和同订单商品、类型的开放申请检查实现幂等和并发去重。`ticket_no`、`request_no` 是各自独立的公开编号。mock 模式使用浏览器本地数据模拟页面流程，remote 模式只调用后端，不在错误时切换为 mock。

数据库结构只由新迁移 `0008_after_sale_ticket_flow` 扩展。定向测试 `backend/tests/test_service_workflow.py` 使用独立的 `aiden_service_flow_test` MySQL 库，运行前需提供 `backend/.env` 中的连接参数，并为同名测试库授予账号权限。

## 本项验证边界

已用不连接用户库的临时 smoke 实际调用业务写入函数、工具与 LangGraph：同 ID 修改正文、版本、生效起止时间或启用状态均拒绝旧快照；三类申请复用写入约束；多商品退款、退货、换货提供已核验订单链接；退货列表跨轮选择保留类型；退款改换货清旧确认；政策变化后的下一轮重新查订单和政策，再给出新确认；无政策时仅给核对/咨询路径；恢复阶段取消不写入。临时脚本已清理。专用单商品退款确认回归测试已通过。

持久化 smoke 使用 Session stand-in，模型、工具 IO 和历史读取使用现有测试 harness，实际执行了 LangGraph，但未连接真实 LLM、未验证真实 MySQL 并发锁竞争或事务提交、未调用外部支付，也未读写用户库数据或配置。独立 MySQL 定向测试契约已同步快照字段，本项未执行会写入数据库的测试；真实持久化验收需另在上述隔离测试库进行。

前端 `tsc` 已通过；实际 Chromium 挂载现有 `UserServicePage`，经 remote 适配器连接仅用于烟测的内存 HTTP fixture，已观察深链预填订单、申请类型与原因，多商品不默认选择商品，以及提交申请、申请进度、工单进度三个页签保留。真实 DOM 操作证明：选择商品并勾选确认后，换商品或编辑原因都会清空确认并禁用提交，编辑本身不发送 POST；正式 POST 包含订单 `ORDER-A`、商品行 `A-2`、类型 `exchange`、当前原因、政策 ID、64 位快照、幂等键及 `confirmed: true`。首次 409 烟测发现同 ID 商品选择被错误清空：独立复现确认预览前后商品 ID 都为 `A-1` / `A-2`，原因仍保留，但延迟执行的 state updater 读取了已复位的 ref；已最小修复为使用回调捕获的刷新标记。修后再次实际 DOM 验证：409 将同 ID 政策由 v1 / `a`×64 更新为 v2 / `c`×64，页面保留仍有效的已选商品 `A-2`、政策及原因 `kept-reason`，确认变为 false、提交禁用且只有第一次 POST；用户重新勾选确认后，第二个 POST 才携带 `A-2`、同一原因与幂等键、`c`×64 新快照。前轮申请进度实际显示过 `AS1 / 换货 / 待审核` 与修改后的原因；另一个独立页面竞态场景已证明慢预览发出后清空 URL query，450ms 迟到响应不回注旧订单/政策，POST 为 0。此次两处 updater 修复后已重新执行 `npx tsc --noEmit`，通过。

上述页面请求完全由临时 fixture 响应，未调用真实后端、MySQL、LLM 或外部支付；“真实 Chromium”指实际页面交互而非真实依赖端到端验收。因环境 Vite 缺少 Rollup 原生包，使用现有 esbuild 临时挂载页面，未安装依赖或更改 package；生产 Vite 构建、完整样式视觉效果及真实依赖联调不在此次验证范围。任务临时脚本、bundle、HTML fixture、HTTP host 和烟测 tabs 已清理；不把这些烟测当作 P0 全链路完成。
