# 客服 RAG 评估说明

本文区分离线四策略检索实验、在线客服图评估和旧版历史报告。题集、报告、模型评审或页面演示都不能单独证明真实演示知识库覆盖；实际语料、集合与服务配置必须看报告 metadata 与来源覆盖清单。
本轮只读 MySQL manifest 观察到 **100 个状态为 `vectorized` 的知识块、来源共 10 个**；状态不代表 FAQ 仍启用、来源文件仍有效，也不代表向量仍存在于 Milvus 有效集合，不能称为 100 个有效或可检索块，更不是此前演示准备的 10 个块。Milvus 配置地址 `19531` 连接被拒，实际 embedding 请求也连接失败，且缺少独立 `EVAL_JUDGE_MODEL` / `EVAL_JUDGE_API_KEY` 配置，因此没有运行真实 v2 评估、没有真实新基线；本轮不启动/补齐依赖、不写库。
本轮 `customer_workflow_v2.jsonl` 的 3 个 gold 来源及章节可在上述 MySQL 状态快照中找到，但 Milvus 拒绝连接，无法核验它们是否位于 MySQL/Milvus 有效集合交集，也没有实际检索结果。这不代表这些题的证据在线可召回。

实现路径的 fixture 验证已完成但不构成真实基线：8 项定向 unittest 通过；完整客服图 fixture 实际执行 assess/generate，threshold 只从 validation 选择 0.2，刻意设置 holdout unsafe=1 未影响选择，进度完成 3/3；四策略调用 smoke 通过；人工抽查导出 2 题、仅导入 1 条后，另一条 pending 保持未处置。售后流程 fixture 另观察到缺原因进入 `reason` 并调用 `query_order`；首次已提供原因进入 `confirm`、调用 `query_order` 和 `query_refund_policy` 但未提交；使用前一真实图结果续跑取消不产生 tools/提交；本人订单查询路由至 `order` / `query_order`。这些是 fixture 和只读/拦截写验证，未向用户数据库写入；judge 质量、真实 embedding、Milvus 召回与线上新指标仍未验收。



## 题集和语料边界

`backend/evals/customer_rag_v1.jsonl` 是文件名保留的 `customer_rag_v2` 题集。每行保留 `id/query/type/difficulty/ground_truth/answer_facts`，新增 `dataset_version/split/semantic_cluster/acceptable_answers/refusal_conditions/expected_refusal/evidence_requirements`。`ground_truth` 为文件与实际章节标题；冲突或示例内容的 `authority_note` 说明标注依据和限制。`validation` 与 `holdout` 按型号/政策语义簇隔离，禁止同簇题目跨集合。不可回答或应拒答不等于没有可核验事实；`expected_refusal` 标出是否应拒绝用户要求的确定结论，`answer_facts` 仍可包含安全说明与建议查询路径。

本题集覆盖知识目录内多个文件，包括型号规格、发票配送和政策示例；这只是评估研究语料，不是当前演示库内容清单。`backend/knowledge/README.md` 当前仅允许按明确清单导入 `商品FAQ.md`，明确不导入 `product-specs.md`、`product-faq.md`、`billing-shipping.md`、`returns-policy.md`、`退货政策.md` 等文件。**不要为让题集通过而扩大默认导入范围，也不要改写或导入用户知识库。** 若独立评估集合使用这些来源，须在独立环境显式准备语料；若目标是评估当前演示集合，应保留缺少的来源并报告覆盖缺口，不得称其已在线验收或用人工拼造的报告代替执行。

同一仓库存在不同运费示例：`product-faq.md` 写未满 99 元收 10 元，`billing-shipping.md` 写 6 元；二者尚无已核准统一口径，gold 要求同时呈现冲突并拒绝选择任意现行金额。漏发等责任不是相反政策版本，来源仅表明尚未授权且须人工核验；退款到账文件也都不支持固定工作日承诺。清洁题限定 FAQ 来源，并记录与规格手册对外套机洗/手洗的差异。上述题不用于宣称知识库已经有权威现行政策。

独立在线题集为 `backend/evals/customer_workflow_v2.jsonl`，覆盖真实意图/工具、知识充分或不足、售后前置核对与确认/拒绝、人工转接。在线图用预置 history 复现工作流状态时，应按题集标记将其理解为状态前置条件，而不是一条端到端真实用户历史。

## 运行

在 `backend` 目录配置可访问的 MySQL、Milvus、embedding、reranker、生成模型及独立评审服务；真实运行不会自动导入语料。评估报告默认写到 `backend/evals/reports/`。真实凭据从本地环境读取，不要将密钥写到命令行历史、报告或提交内容。Windows PowerShell 示例：

```powershell
# 独立评审凭据来自本地环境；EVAL_JUDGE_API_KEY 是默认密钥变量名
python -m evals.run_customer_rag `
  --mode offline `
  --dataset evals/customer_rag_v1.jsonl `
  --collection knowledge_bm25 `
  --report evals/reports/customer_rag_v2.json

# 只跑四策略检索，不调用生成与judge
python -m evals.run_customer_rag --mode offline --retrieval-only `
  --dataset evals/customer_rag_v1.jsonl `
  --report evals/reports/customer_rag_v2-retrieval-only.json

# 在线工作流按 validation 比较阈值，冻结所选阈值后再独立报告 holdout
python -m evals.run_customer_rag --mode online `
  --dataset evals/customer_workflow_v2.jsonl `
  --thresholds 0.2,0.35,0.5 `
  --report evals/reports/customer_workflow_v2.json
```
两种 mode 分别产出 v2 报告：离线默认报告 `evals/reports/customer_rag_v2.json`，在线工作流报告 `evals/reports/customer_workflow_v2.json`。员工后台的 `evaluate` 与 `evaluate-online` job 分别写这两个文件；CLI 用 `--mode offline` / `--mode online` 分别运行，建议像上面一样显式设置对应的 `--report`，一条 CLI 命令不会混跑或覆盖两种 mode 的报告。


生成评估默认要求独立 judge：`EVAL_JUDGE_MODEL`、`EVAL_JUDGE_API_KEY`，可用 `EVAL_JUDGE_BASE_URL` 配置 provider，也可通过 `--judge-model`、`--judge-base-url`、`--judge-api-key-env` 指定。默认密钥环境变量是 `EVAL_JUDGE_API_KEY`。judge 与回答生成必须采用不同 provider/model；只有明确接受相关性风险时才用 `--allow-shared-judge`。报告记录 judge 名称、是否独立及模型 usage；服务不提供 token usage 时保留 `null`，不做伪精确估算。

在线评估直接运行客服图 `assess_knowledge()` / `generate()` 和真实工具链，不等同于离线四策略实验。默认只读：不保存会话、拦截业务写工具，也不创建人工接管记录；转人工只评估 handoff decision，不 commit 到人工队列。在线题的只读账户可由 `workflow.user_id` 指定，或用 CLI `--isolated-account` / 环境变量 `EVAL_ACCOUNT_ID` 指定既有账户；如果没有可核验账户/订单，runner 在 `preconditions.status` 记为 `missing_account`、`account_not_found` 或 `order_not_found`。未满足前置条件的 case 保留在报告中，但不计入 `scored_count` 的成功评分，汇总另显示 `preconditions_unmet_count`；不要把它们当作意图或流程错误。

如需启用业务写入，必须显式传入 `--allow-writes --isolated-account eval_<专用账户> --isolated-environment <隔离环境名>`，且本地环境变量 `EVAL_ISOLATED_ENVIRONMENT` 必须与 `--isolated-environment` 参数完全一致。题目需提供该 eval 账户已有 workflow 的 `conversation_id` 与 `assistant_message_id`；runner 校验二者归属该账户，不会自动创建。还必须显式传入单一阈值，例如 `--thresholds 0.2`；默认多候选阈值扫描不能写入。即使在隔离写入模式，评估也不保存会话或消息，handoff 仍只评估 decision、不提交人工队列。


## 报告如何读

新报告 `schema_version=2` 带 `evaluation_mode`、`execution_environment`、dataset hash、语料/集合/模型 metadata、逐题结果和人工抽查状态。`metadata.corpus_manifest.sha256` 是 MySQL `vectorized` 内容快照的 hash；`metadata.collection_manifest.sha256`（同时用于 `collection_version`）是 Milvus 集合 schema、向量与 BM25 文本内容的 hash。两份 manifest 各自描述自己的快照，不能相互替代。语料来源覆盖以 MySQL `vectorized` 内容与 Milvus 集合实际 chunk ID 的交集为准：报告中的 `effective_collection_sources` / `effective_collection_chunks` 描述交集覆盖，`unobserved_sources` 标出该集合中未观察到的语料来源。检索到的来源列表不是语料全集清单，不能据此推断全集完整。offline 的 `strategies` 比较四种检索策略；online 的 `strategies.online` / `workflows` 是真实在线图结果。两种 mode 指标不应混为一组。


除 Recall/MRR/Faithfulness 外，新报告展示答案完整性、误拒答、应拒未拒、延迟、生成 token 与 judge token；缺失 usage 保持未知。Faithfulness 只衡量答案事实是否被本轮证据支持，不等价于答案完整、政策已授权或业务流程安全。Online 的 intent/tool/refund/handoff 与节点轨迹用于逐题核对路由、工具与售后阶段；若 workflow 没有配置某类断言，其指标为未知而不是零。

在线阈值候选只在 `validation` 上比较，选定后冻结并报告独立 `holdout`；不能反复依据 holdout 结果调阈值后再继续称其留出集。默认候选值是实验配置而非达标阈值，项目没有预先捏造通过率目标。先核验题目标签和validation行为，再对holdout做一次独立检查；语料或题集 hash 改变必须生成新报告，不能把旧结果升级为新基线。

初始 15 题的 `backend/evals/reports/customer_rag_v1.md` 与旧 JSON 是历史快照，不能当成 v2 新题集或新指标基线。兼容 API `/api/rag/evals/customer-rag-v1` 优先返回 v2 offline 报告；无新报告时返回旧报告并标为 `schema_version=1`、`legacy=true`、历史环境未经核验。在线报告另由 `/api/rag/evals/customer-workflow-v2` 提供。

## 人工抽查与校准

自动 judge 不能替代人工复核。先导出待抽查题目：

```powershell
python -m evals.run_customer_rag `
  --review-from evals/reports/customer_rag_v2.json `
  --export-reviews evals/reports/customer_rag_v2-reviews.json `
  --report evals/reports/customer_rag_v2-review-template.json
```

人工抽查只填写实际抽中的行，不要求把导出的所有行填完。对抽中行填写 `status`（`accepted` 或 `disagreed`）、`reviewer` 与 `notes`，重点检查版本冲突、否定条件、多证据、库外拒答、政策权威边界和误拒答。导入时未填写的 `pending` 行会跳过，不必为凑齐导出清单而逐行确认；导入仅应用已填写的人工结论，保留原自动评审与抽查说明：

```powershell
python -m evals.run_customer_rag `
  --review-from evals/reports/customer_rag_v2.json `
  --import-reviews evals/reports/customer_rag_v2-reviews.json `
  --report evals/reports/customer_rag_v2-reviewed.json
```

调整阈值只依据 validation 的明确错误与人工审阅结果，记录候选值、所选阈值和理由；不按 holdout 调参。若 source/section、预期拒答或答案事实标注需改变，先修题集、核验章节及 semantic cluster，再重跑生成/评审，不能只对旧召回报告重算并把旧 judge结果算作新基线。

## 员工页面

remote 员工页面 `/staff/evals` 读取 `/api/rag/evals/customer-rag-v1` 的离线报告，可启动 `evaluate` 离线任务；在线模式从 `/api/rag/evals/customer-workflow-v2` 读取，可启动 `evaluate-online`。页面需标明报告模式、真实/fixture 环境、历史报告状态、分割集与模型配置；fixture 结果仅供确定性验证，不代表真实模型或知识库效果。mock 模式不生成假报告。

真实 Chromium + 隔离 HTTP fixture 的完整页面 smoke：offline 四策略展开，null score 显示 `—`、正常回答 tag computed RGB `(56, 158, 13)`、token 30/60/90/120 分别展示且不合并、unknown 保持未知；online 的 intent/tool/refund/handoff/blocked 五项指标可见（scored=1、前置未满足=1、selected threshold=0.2、holdout=1），handoff decision 未 commit、未保存消息并拦截 blocked tools；legacy 警告和展开正常。全程仅 GET、无 POST/job、`errors=[]`。同时验证 `.eval-main { grid-template-columns: minmax(0, 1fr) }` 修复：scrollWidth 从 2158 收敛至 viewport 1536，card 宽 1320。该 HTTP fixture UI smoke 不代表真实模型/语料基线。

最终集成时并发提交基线 `3aa3781` 的两处 SSE validation 事件落入非法 dict/else 位置，作为真实评估图可导入的必要前提，仅将这两处既有事件移至正确缩进（4 个 hunk），保持原事件意图；不纳入 recognition 前移，也不扩展 SSE 功能。将修复后的 task-only Git tree 只读导出至临时目录，5 个评估相关 Python 模块的 AST 与导入通过，并从该目录实际运行知识图 fixture：同一 MH-LP50 问题在 threshold=0.2 输出带 `[1]` 的回答，在 threshold=0.8 输出“现有知识库证据不足”；两次均执行 `assess_knowledge` / `generate`，intent=`product`、tool=`search_faq`、handoff committed=false。该验证未调用真实依赖、未读写用户业务历史/消息，也不证明真实模型或语料效果；用户工作区与真实 index 均未用于重写或暂存。
