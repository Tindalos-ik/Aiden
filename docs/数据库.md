# Aiden 数据库实现总结

## 本次完成内容

- 使用 Docker Compose 部署 MySQL 8.4，配置 utf8mb4、命名数据卷、健康检查和可配置的本机端口；Compose 只启动数据库。
- 新增环境变量示例 deploy/.env.mysql.example，包含数据库账号、占位密码、端口和本机连接用的 DATABASE_URL；没有创建或写入真实密码文件。
- 使用 SQLAlchemy 2.x 为 19 张表建立 ORM：原有用户、登录会话、商品、SKU、订单、订单商品、包裹、物流轨迹、售后申请、政策、FAQ、知识块、会话、消息、工单和未解决问题，加上对话挖掘批次、问答候选暂存与低置信度问题池。
- 为模型定义主键、外键、唯一约束、状态检查和常用查询索引。金额使用 DECIMAL/Decimal；订单商品保留名称、规格、SKU 和成交价快照；政策按键和版本唯一，并记录生效区间。
- 增加 Alembic 初始迁移以及读取 DATABASE_URL 的延迟 Engine/Session 代码。导入模型不会自动建表。
- 提供按用户读取订单、按用户和订单读取物流轨迹、查询指定时点的生效政策、按用户读取会话消息等数据访问方法。订单、物流和会话消息查询都在 SQL 中限制 user_id。
- 客服 Agent 已接入 `query_order`、`query_logistics`、`search_faq` 三个只读工具；查询参数、结果字段、空结果和权限说明见 [`tools.md`](tools.md)。订单与物流工具直接查询已有订单、包裹和轨迹表；`search_faq` 先经 Milvus 召回、再回 `knowledge_chunks` 取原文。
- 离线建库由 `0004_knowledge_chunks` 新增知识块表，`0005_conversation_mining` 新增对话挖掘批次和候选暂存表，并加宽知识块内容类型字段。Markdown、FAQ 与历史对话问答都先写 MySQL，再补齐 Milvus 向量；表结构、状态流转和命令见 [`数据层.md`](数据层.md)，检索与员工控制台见 [`RAG.md`](RAG.md)。
- [`数据层.md`](数据层.md) 说明表关系、字段假设和知识数据流；本文下方列出 PowerShell 环境配置、启动 MySQL、执行迁移和关闭容器的方法。
- 数据库依赖独立列在 backend/requirements-db.txt。

## 数据层接入入口

从 backend 目录运行服务并导入：

- app.persistence.mysql.get_session：可用作 FastAPI 依赖的 Session 生成器。
- app.persistence.mysql.session_scope：自动提交或回滚的事务上下文管理器。
- app.persistence.mysql.get_engine 和 app.persistence.mysql.get_session_factory：根据进程环境中的 DATABASE_URL 延迟创建并缓存引擎与 Session 工厂。
- app.persistence.mysql.models：19 张表的 ORM 类和 Base。
- app.persistence.mysql.queries：list_user_orders、get_owned_order_with_shipments、list_order_tracking_events、get_effective_policy、list_conversation_messages。
- app.persistence.mysql.knowledge：knowledge_chunks 的写入、状态流转与读取；在线检索回表用 get_vectorized_chunks_by_ids。

客服 Agent 的订单和物流工具从 LangGraph 状态注入当前认证用户 ID；知识库是商城公共内容，不按用户隔离。订单号通过 SQLAlchemy 表达式绑定参数，不拼接 SQL。工具只把回答需要的订单商品、物流节点或知识条目字段交给模型；异常返回通用提示，不向用户暴露数据库细节。

## 本机操作

从项目根目录复制并编辑环境示例，设置本机密码，并保持 DATABASE_URL 与账号、数据库名和端口一致：

    Copy-Item deploy/.env.mysql.example deploy/.env.mysql
    docker compose --env-file deploy/.env.mysql -f deploy/compose.mysql.yml up -d mysql
    Set-Location backend
    python -m pip install -r requirements-db.txt
    $urlLine = Get-Content ..\deploy\.env.mysql | Where-Object { $_ -match '^DATABASE_URL=' } | Select-Object -First 1
    $env:DATABASE_URL = $urlLine.Substring('DATABASE_URL='.Length)
    .\.venv\Scripts\alembic.exe -c alembic.ini upgrade head

迁移完成后从 backend 返回项目根目录并关闭容器：

    Set-Location ..
    docker compose --env-file deploy/.env.mysql -f deploy/compose.mysql.yml down

down 会保留命名数据卷。真实密码只放本机环境文件，不要提交。

## 客服工具的数据库边界

- 订单查询最多返回当前用户最近 5 笔订单；传入订单号时仍须同时匹配当前用户 ID。
- 物流查询通过当前用户拥有的订单关联包裹与物流节点。没有匹配订单时返回空包裹列表，不会仅凭订单号读取其他用户数据。
- `search_faq` 不查 `faq` 表，而是在 Milvus 2.5+ 中以 dense 与原生 BM25 各召回 Top-50、RRF 融合，再回 `knowledge_chunks` 读取有效原文并用 bge-reranker-v2-m3 精排，默认最多返回 10 条。品类等标量条件可在召回前过滤。
- 知识库无匹配、订单无匹配或订单没有包裹时均返回明确的空结果。当前工具还覆盖本人售后申请与工单进度；用户售后页面从 `policies` 表读取有效版本，Agent 的政策回答则引用知识库证据。
- `0006_rag_answer_evidence` 为 `messages` 增加 `citations` JSON 快照，并创建 `low_confidence_questions`：原始问法、来源会话、入池入口、证据不足原因、创建时间。生成节点拒答时，问题池记录与助手最终消息同事务提交；历史消息返回引用快照。知识工具仍只读，不修改知识表。
- `0008_after_sale_ticket_flow` 为售后申请增加幂等键、政策来源、审核人与处理时间，为工单增加售后申请关联、接手和结单时间。申请与工单归属由复合外键约束；具体状态及 API 见 [`售后与工单.md`](售后与工单.md)。
- `0009_low_confidence_feedback` 为 `messages` 增加可空的 `feedback`（`satisfied` / `unsatisfied`），为 `low_confidence_questions` 增加可空的来源用户消息 ID 和助手消息 ID；旧行保持可读，不回填推测来源。自动拒答按失败诉求逐条入池，同一条助手完成事务原子提交；负反馈在核验用户、消息和真实问题后，同事务记录反馈和入池，重复请求及并发请求只保留一次，正反馈只保存状态。问题池只负责记录待处理问法，人工审核和自动补库尚未实现。
