# Aiden MySQL 数据层

本地 MySQL 使用 MySQL 8.4，ORM 使用 SQLAlchemy 2.x，迁移使用 Alembic。数据层代码位于 backend/app/persistence/mysql/。导入模型或会话模块不会创建数据库表；表结构只由 Alembic 迁移管理。

## 表与关系

| 表 | 主要字段与用途 | 关系 |
| --- | --- | --- |
| **users** | **id**、**name**、唯一 **email**、可选且唯一的 **phone**、**role**、可选 **password_salt/password_hash** | 用户拥有订单和会话；客服账号可被指定为会话、工单负责人 |
| **login_sessions** | **token_hash**、**user_id**、**expires_at**、**created_at** | 只保存 HttpOnly Cookie 令牌的 SHA-256 哈希；按用户外键级联清理 |
| **products** | **name**、**category**、**description**、**is_active** | 一个商品有多个 SKU |
| **product_skus** | 商品外键、唯一 **sku_code**、规格 JSON、**price**、**stock_quantity**、**is_active** | 属于一个商品；订单行可选关联当前 SKU |
| **orders** | 唯一 **order_no**、**user_id**、**total_amount**、**currency**、**status**、**ordered_at** | 属于一个用户；包含订单行和包裹 |
| **order_items** | **order_id**、可空 **sku_id**、商品/SKU 名称与规格快照、**quantity**、**unit_price**、**line_total** | 属于一个订单；删除 SKU 后保留订单快照 |
| **shipments** | **order_id**、包裹号、承运商、运单号、配送 **status**、发货/签收时间 | 一个订单可有多个包裹 |
| **tracking_events** | **shipment_id**、节点代码、状态、地点、描述、**occurred_at** | 属于一个包裹；按包裹和发生时间索引 |
| **after_sale_requests** | 唯一申请号、用户/订单/订单行、申请类型、原因、处理状态、申请金额 | 复合外键确保用户确为订单所有者、订单行确属该订单 |
| **policies** | **policy_key**、**name**、**version**、正文、**effective_from/effective_until**、**is_active** | **(policy_key, version)** 唯一；可保留同一政策的多个版本 |
| **faq** | 分类、问题、答案、**is_active** | 独立问答条目 |
| **knowledge_chunks** | 唯一 **chunk_key**、来源类型与标识、**category**、**questions**、**answer**、章节路径、内容类型、关键条款标记、前后块指针、**vector_status**、**vector_id** | 离线知识库的原文与向量化状态；**id** 同时是 Milvus 集合主键 |
| **conversation_mining_batches** | 唯一 **batch_signature**、**conversation_id**、**run_id**、**status**、窗口首末消息时间、窗口消息 id 列表、`turn_count`、`candidate_count`、`error_message` | 历史对话挖掘的抽取窗口与进度；只引用 **conversations**，删除会话时级联删除 |
| **conversation_qa_candidates** | 唯一 **candidate_key**、**batch_id**、**conversation_id**、**question**、**answer**、**category**、来源消息标识、**evidence**、**confidence**、**status**、**rejection_reason**、**answer_fingerprint** | 入库前的问答候选暂存；只引用 **conversation_mining_batches**，删除批次时级联删除 |
| **conversations** | **user_id**、主题、状态、接管客服、开始/结束时间、**last_message_preview** | 属于一个用户；复合唯一键供工单校验归属 |
| **messages** | **conversation_id**、发送者角色、内容、发送状态、**client_message_id**、**created_at** | 属于一个会话；删除会话时级联删除消息；客户端重试键不作为主键 |
| **tickets** | 唯一工单号、会话/用户、问题类型与描述、状态、负责人、解决时间 | 复合外键保证工单的用户与会话所有者一致 |
| **unanswered_questions** | 会话、问题、可选置信度、审核状态、审核人/备注/时间 | 关联产生该问题的会话，可记录人工审核结果 |

用户、商品、订单、会话等主键采用应用生成的 UUID 字符串（36 字符）。外键默认限制删除有业务记录的用户、商品和订单；消息及物流节点随其会话或包裹清理。关键关联列均有索引，订单号、工单号、SKU 编码、邮箱、手机号和政策键/版本有唯一约束。订单商品保存购买时的商品名、规格、SKU 编码和成交价，目录数据后续变化不会改写订单历史。

## 字段约定

- 金额用 DECIMAL(12, 2)，ORM 类型标注为 decimal.Decimal；订单保存币种，默认 CNY。SKU 当前售价与订单成交价分开存储。
- MySQL DATETIME 不携带时区；应用将时间按 UTC 写入，并在读取/展示边界转换时区。政策有效期采用左闭右开区间：effective_from <= 查询时间 < effective_until，结束时间为空表示无截止日期。
- 用户密码只存盐和哈希字段，不存明文；二者可空，以支持由外部身份系统管理凭据的账号。手机号允许空值，MySQL 对唯一索引中的多个 NULL 不视为冲突。
- orders.status、包裹状态和政策内容不做固定枚举约束，便于接入外部订单状态和后续政策格式；会话、消息、售后、工单、问题池等内部流程状态有检查约束。
- after_sale_requests 的 user_id、order_id 和 order_item_id 通过复合外键保持所属关系一致。工单也通过 (conversation_id, user_id) 复合外键校验所有者。
- unanswered_questions 必须关联一个会话；问题审核状态包含待审核、已审核、已补入 FAQ 和忽略。
- 前端消息的 `role` 映射到 MySQL 的 `sender_role`；`client_message_id` 最长 100 字符，与 36 字符消息主键分开保存，并按会话和发送角色唯一约束。用户消息与流式助手消息在一个短事务中创建。
- 消息时间使用 `DATETIME(6)` 保存微秒，保留用户消息与对应助手占位消息之间的 1 微秒顺序，避免同一秒内由随机 UUID 决定显示位置。
- 所有 MySQL `DATETIME` 按 UTC 写入；API 在返回边界补上 UTC 时区并序列化为 ISO 8601（`Z`）字符串。
- `knowledge_chunks.content_type` 长度按中文字面值留足（VARCHAR(64)）：文档切分产生 text、table、code、mixed，对话挖掘产生可读的「对话挖掘问答」。
- `knowledge_chunks.questions` 在对话挖掘来源下保存对话中的真实问法；`source_type` 为 `conversation`，`source_id` 为 `conversation-qa:<规范化问法集合哈希>`，与该来源在 `knowledge_chunks` 中的幂等作废判定配套。
- 对话挖掘的批次签名对「会话 id + 窗口内消息 id 与发送角色序列」取哈希，候选键由批次签名与候选序号决定，两者都是唯一约束，因此重复运行不会重复抽取同一批消息或重复生成候选。
- 对话挖掘的 `first_message_at` / `last_message_at` 使用 `DATETIME(6)`，与 `messages.created_at` 的微秒精度一致，续跑锚点比较才不会被截断到秒而重复或漏读同一秒内的消息。

## Alembic 的作用

SQLAlchemy 模型描述代码当前期望的表结构；Alembic 负责把结构变化保存成有序、可复用的迁移版本。这样新建数据库或部署到新环境时，可以按同一顺序创建表；以后新增列、索引或表时，也能明确记录这次结构变更，而不依赖服务启动时临时建表。

执行迁移后，Alembic 会在数据库中维护 alembic_version 表，记录已应用到哪个迁移版本。执行 upgrade head 时，它会从当前版本开始，依次执行尚未应用的迁移，直到项目中的最新版本。Aiden 当前依次执行 0001 初始结构、0002 对话服务字段变更、0003 消息时间精度修复、0004 知识块表、0005 对话挖掘暂存表。

新增结构变更时，应创建一份新的迁移脚本并检查其 upgrade 和 downgrade 操作，再对目标数据库执行迁移。已有迁移作为历史记录保留；修改 ORM 模型本身不会自动修改数据库表。downgrade 可以按迁移脚本尝试回退结构，但不能代替数据备份，且删除列等回退操作可能丢失数据。

常用命令（在 backend 目录，且已设置 DATABASE_URL）：

    # 应用所有尚未执行的迁移
    .\.venv\Scripts\alembic.exe -c alembic.ini upgrade head
    # 为后续结构变更生成迁移草稿，生成后需检查脚本再应用
    .\.venv\Scripts\alembic.exe -c alembic.ini revision --autogenerate -m "describe schema change"
    # 按迁移脚本回退一个版本；操作前应确认数据影响
    .\.venv\Scripts\alembic.exe -c alembic.ini downgrade -1

## 本机启动与迁移（PowerShell）

以下命令从仓库根目录运行。后端需要 Python 3.10 或更新版本；若本机 `python` 指向旧版本，请在命令中换成已安装的较新解释器。示例文件只有占位密码；复制后请在本机编辑 deploy/.env.mysql，并让 DATABASE_URL 中的用户名、密码、数据库名和端口与 MySQL 变量一致。真实密码不要提交。若密码包含 URL 保留字符，需在 DATABASE_URL 中按 URL 规则编码。

    Copy-Item deploy/.env.mysql.example deploy/.env.mysql
    # 编辑 deploy/.env.mysql 中的 MYSQL_PASSWORD、MYSQL_ROOT_PASSWORD 和 DATABASE_URL
    docker compose --env-file deploy/.env.mysql -f deploy/compose.mysql.yml up -d mysql
    docker compose --env-file deploy/.env.mysql -f deploy/compose.mysql.yml ps
    Set-Location backend
    # requirements.txt 同时安装 API、Agent 与 MySQL/Alembic 运行依赖
    .\.venv\Scripts\python.exe -m pip install -r requirements.txt
    $urlLine = Get-Content ..\deploy\.env.mysql | Where-Object { $_ -match '^DATABASE_URL=' } | Select-Object -First 1
    $env:DATABASE_URL = $urlLine.Substring('DATABASE_URL='.Length)
    .\.venv\Scripts\alembic.exe -c alembic.ini upgrade head
    # 创建本地演示用户（已存在且无冲突的账号会保留）
    .\.venv\Scripts\python.exe -m scripts.init_demo_users
    # 启动 FastAPI（DATABASE_URL 沿用当前 PowerShell 会话）
    .\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000

关闭容器（命名数据卷保留，下次启动可继续使用）：

    Set-Location ..
    docker compose --env-file deploy/.env.mysql -f deploy/compose.mysql.yml down

deploy/.env.mysql 是本机配置，不要提交；应提交的只有 deploy/.env.mysql.example。Compose 只启动 MySQL 服务，不包含 FastAPI。

## 客服只读工具

客服 Agent 已通过 `backend/app/services/tools/` 接入三个只读查询工具，完整参数、返回字段、权限边界和流式行为见 [`tools.md`](tools.md)：

- `query_order` 从当前用户的订单中按订单号精确筛选；未提供订单号时最多返回最近 5 笔，并带订单商品快照。
- `query_logistics` 先按 `user_id` 和订单号确认订单归属，再经订单关系读取包裹和物流节点。未知订单号和其他用户的订单号都返回空结果。
- `search_faq` 走在线语义检索：问题经 BGE 服务编码成 dense 向量，在 Milvus `knowledge` 集合召回候选，再按主键回到 `knowledge_chunks` 取权威原文，只接受 `vector_status = 'vectorized'` 的块，最终默认返回 5 条问题、答案和分类。

身份由会话路由从认证 Cookie 解析后写入 LangGraph 状态，再通过 `InjectedState` 注入订单和物流工具；模型可见的工具参数不包含 `user_id`。订单与物流工具使用 SQLAlchemy 查询和短生命周期 Session，不修改数据，也不需要新增表或迁移；知识检索见本文的「离线建库」与 [`RAG.md`](RAG.md#在线语义检索)。

## 离线建库（RAG）

本节从数据角度说明已实现的离线建库能力：把 Markdown 知识文档和现有 faq 行写入 MySQL，再向量化到 Milvus。切分算法、向量服务、Milvus 集合结构、配置项与验证结果的完整说明见 [`RAG.md`](RAG.md#离线建库)，在线检索见 [`RAG.md`](RAG.md#在线语义检索)。另一段离线能力（从历史客服对话挖知识）见本文的「历史对话挖掘」一节。两段离线能力产生的知识都由 `search_faq` 在线检索。

`docs/Aiden.md` 的 RAG 章记录了目标设计与选型过程，其中包含尚未实现的规划内容。已实现的离线建库行为以本节和 [`RAG.md`](RAG.md#离线建库) 为准。

### 知识块与原文归属

原文的权威来源是 MySQL 的 `knowledge_chunks` 表，Milvus 只承担相似度检索。每个来源的知识块由 `app.services.rag.indexing` 中的 `index_markdown_file` 与 `index_faq_rows` 写入，两者都调用 `app.persistence.mysql.knowledge` 中的 `upsert_source_chunks`。

来源有两类。Markdown 文档以相对路径标识（`markdown:<相对路径>`），经 `app.services.rag.knowledge` 中的 `parse_markdown_document` 按标题层级解析成章节树，再由 `build_document_chunks` 逐章节切分。现有 faq 行以 `faq:<行 id>` 单独标识，由 `build_faq_chunks` 转成知识块，只读取 `is_active` 为真的行，不修改 `faq` 数据。

每块记录 `category`、`questions`、`answer` 和章节路径。Markdown 块没有天然问法，`questions` 只使用所属章节标题，`category` 使用完整上级标题路径（根章节退回文档标题）。FAQ 块使用真实问题作为 `questions`，用自己的分类作为 `category`；对话挖掘入库的问答使用脱敏后的真实问法。

只有 `category`、`questions`、`answer` 三项会拼成向量化文本，格式由 `app.services.rag.embedding_text` 中的 `build_embedding_text` 单点定义。章节路径、内容类型、关键条款标记和前后块指针只作为元数据保存。每块另存 embedding_text（当时实际送去向量化的文本）和 embedding_fingerprint（拼接模板版本），便于区分模板变更与正文变更。

关键条款通过标题关键词判断，命中退货、退款、换货、售后、保修、质保、赔付、运费险、发票或退换的章节会被标记，供后续检索排序加权。

### 向量状态与中断补齐

`vector_status` 有四个取值。`pending` 表示原文已入库、尚未向量化；`vectorized` 表示向量已写入 Milvus 并回填 `vector_id`；`need_manual_review` 表示块或单句超过模型可编码长度，写 MySQL 但不进 Milvus，等人工拆分；`superseded` 表示该块已失效，不再作为知识。

`app.services.rag.indexing` 中的 `vectorize_pending` 负责把 `pending` 块补齐，顺序是先算向量、再写 Milvus、成功后才回填状态。Milvus 的向量主键就是 knowledge_chunks 的主键，写入使用 upsert，因此覆盖式重写不会产生重复向量，这正是「Milvus 已写入、MySQL 尚未回填」这个中断窗口可以安全重跑的原因。

内容更新或块数量变化时，`upsert_source_chunks` 把本次未生成的旧块置为 `superseded` 并清空 `vector_id`，`cleanup_superseded_vectors` 再按这些 id 去 Milvus 删除向量。判定作废用主键差集，不用时间戳比较。

早期方案曾设想由 Milvus 分配 ID，`docs/Aiden.md` 现已同步为实际实现：MySQL 主键同时用作 Milvus 主键，`vector_id` 回填的就是该主键。若由 Milvus 生成 ID，中断窗口下应用不知道上次写入的向量 ID，重跑可能重复插入。

另外，若整库被重建或整表被清空，MySQL 侧不再有 `superseded` 记录，Milvus 中的旧向量会变成孤儿；此时只能用 `MILVUS_KNOWLEDGE_COLLECTION` 换集合名，或手动删除该集合重建。

### 切分与长度计量

切分由 `app.services.rag.chunking` 中的 `chunk_section` 完成：章节直属正文需要拆分时按完整句子装箱，重叠只取上一块新增内容的尾部完整句子，同时满足重叠预算和下一块预算；每个子章节递归处理，达到标题深度上限也不会丢弃子章节。单句超过生效单句上限时整句保留并标记 `need_manual_review`，不做静默截断。Markdown 表格由 `split_markdown_table` 按数据行分块，每块复制表头且独立输出；超长表头、单行或代码块也需人工审核。精确计量模式按实际拼接文本计算 token 数。

长度计量由 `app.services.rag.length` 中的 `get_length_meter` 提供，有两种模式。配置 `EMBEDDING_TOKENIZER_PATH` 指向本地 `tokenizer.json` 且安装 `tokenizers` 时，对实际拼接文本按子词精确计数；否则按字符估算，并把 `RAG_MEASUREMENT_UNCERTAINTY_TOKENS` 与 `RAG_SAFETY_MARGIN_TOKENS` 计入预算。设置 `RAG_REQUIRE_EXACT_TOKENIZER=true` 时不能退回估算。

单块预算在 `app.config.rag` 的 RagSettings 中推导，同时受 RAG_MAX_CHUNK_TOKENS 与 EMBEDDING_MAX_SEQ_TOKENS 约束，取两者较小值。换成上下文较短的模型时必须同步调小 EMBEDDING_MAX_SEQ_TOKENS，否则块会超过模型可编码长度而被推理服务截断。

### 向量服务

向量服务由 `backend/scripts/embedding_server.py` 提供，按 OpenAI 兼容协议暴露 `/v1/embeddings`，只监听 127.0.0.1，模型权重与推理都在本机完成。本项目按 CPU 推理部署，不需要显卡或 CUDA。`backend/scripts/setup_embedding_server.ps1` 负责准备独立虚拟环境，装 CPU 版 torch，依赖与后端 requirements.txt 隔离。

    # 准备环境（CPU 版，约 0.3 GB，只需执行一次）
    .\backend\scripts\setup_embedding_server.ps1
    # 启动服务（前台运行，需保持该终端开启）
    D:\bge-m3-env\Scripts\python.exe backend\scripts\embedding_server.py --model BAAI/bge-m3
    # 一键探测并把真实维度回写到 backend/.env
    .\backend\scripts\verify_embedding_service.ps1 -Model BAAI/bge-m3

CPU 推理下不要传 `--fp16`，该参数只在 GPU 上有效。应用侧由 `app.services.rag.embedding` 中的 `EmbeddingClient` 调用，它会把实际返回的向量维度与 EMBEDDING_DIMENSION 比对，不一致直接报错，避免写错维度污染集合。模型缓存位置由 HF_HOME 决定；无法直连 HuggingFace 时把 HF_ENDPOINT 设为镜像地址。详细的准备与启动说明见 [`RAG.md`](RAG.md#离线建库) 的向量服务一节。

### 建库命令

命令位于 `backend/scripts/build_knowledge_base.py`，都在 backend 目录下执行，连接与凭据全部来自 `backend/.env`。

    # 导入 Markdown 目录（缺省用 RAG_KNOWLEDGE_DIR，即 backend/knowledge）
    .\.venv\Scripts\python.exe -m scripts.build_knowledge_base import-markdown
    # 导入启用中的 faq 行
    .\.venv\Scripts\python.exe -m scripts.build_knowledge_base import-faq
    # 扫描待向量化块并补齐；退出码 1 表示仍有遗留
    .\.venv\Scripts\python.exe -m scripts.build_knowledge_base vectorize
    # 只看还有多少待处理，不写数据
    .\.venv\Scripts\python.exe -m scripts.build_knowledge_base scan-pending
    # 删除已作废块的旧向量
    .\.venv\Scripts\python.exe -m scripts.build_knowledge_base cleanup-vectors
    # 各状态的块数与当前配置
    .\.venv\Scripts\python.exe -m scripts.build_knowledge_base stats

导入本身幂等：`chunk_key` 由来源、块序号与内容哈希决定，内容未变时重导入只更新行，不会把已向量化的块打回待处理，也不会产生新向量。因此内容变更后重复执行导入与向量化即可，无需清理。

### 在线检索的读取入口

`app.persistence.mysql.knowledge` 提供三个只读接口。`get_vectorized_chunks_by_ids` 是在线检索的回表接口：按主键批量取原文，同时要求 `vector_status = 'vectorized'`，返回顺序与传入的主键顺序一致。`get_chunks_by_ids` 不做状态过滤，供运维排查使用。`list_knowledge_chunks` 按分类分页读取未被作废的知识块，供人工核对切分结果，不是检索接口。

过滤必须落在 SQL 里，而不是读回来再筛：Milvus 与 MySQL 允许短暂不一致，命中项可能仍是 `pending`（回填前中断）、已 `superseded`（旧向量尚未删除或索引尚未收敛），或是在整库重建后残留的孤儿向量。这些命中项一律不能交给 Agent。

## 历史对话挖掘

本节从数据角度说明第二段离线能力：从 `conversations`、`messages` 的历史客服对话中抽取问答知识。抽取流程、脱敏规则、去重判定、状态机与验证结果的完整说明见 [`RAG.md`](RAG.md#历史对话挖掘)。入库的知识与文档、FAQ 走同一套向量化流程，因此同样可以被 `search_faq` 检索到。

### 数据来源与只读边界

数据源是现有的 `conversations` 与 `messages` 两张业务表，只做 SELECT，不改动任何业务数据。读取时只取 `messages.status = 'complete'` 的消息：`streaming` 还在生成，`error` 与 `stopped` 都不是可信答案，把它们当依据会把半截回答变成知识。`system` 消息也不参与。

读取按 `(created_at, id)` 升序，与消息表索引一致，保证同一批数据每次运行顺序相同。每个会话从「已处置批次的最后消息时间」之后继续读，因此已处理过的消息不会被重复读取。会话按最早活动时间升序处理，积压数据按时间顺序补齐。

### 两张新表

`0005_conversation_mining` 新增两张表，并把 `knowledge_chunks.content_type` 从 VARCHAR(16) 加宽到 VARCHAR(64)。该迁移不修改任何既有业务表。

**conversation_mining_batches**：一行代表「某个会话中由固定消息序列组成的一段抽取窗口」，是抽取与续跑的进度单位。

| 字段 | 含义 |
| --- | --- |
| batch_signature | 唯一，对「会话 id + 窗口内消息 id 与发送角色序列」取哈希 |
| conversation_id | 窗口所属会话，外键级联删除 |
| run_id | 认领该批次、真正调过模型的那一次运行；待抽取批次为空。仅用于追溯抽取轮次，不限定整体去重范围 |
| claimed_by | 认领该批次的运行标识 |
| status | 批次状态，取值见下 |
| first_message_at / last_message_at | 窗口边界，DATETIME(6)，用于推进续跑锚点 |
| message_ids | 窗口内消息主键列表，JSON |
| turn_count / candidate_count | 窗口内完整问答轮次数与写入的候选条数 |
| error_message | 失败或跳过原因，截断到 500 字符 |
| extracted_at / promoted_at | 抽取完成与入库完成时间 |

批次状态与含义：

| 状态 | 含义 | 是否推进续跑锚点 |
| --- | --- | --- |
| pending | 窗口已确定，尚未调用模型 | 否 |
| extracting | 已被某次运行认领，正在调模型 | 否 |
| extracted | 抽取完成、候选已写入暂存表 | 否 |
| ready | 已抽取完成，等待全局候选池整体去重 | 否 |
| promoted | 本批次参与的去重与入库已完成 | 是 |
| skipped | 已处置但没产生知识（候选全是重复或冲突、单轮超长、窗口内无完整轮次） | 是 |
| failed | 调用模型或校验失败，保留错误信息，可重跑 | 否 |
| superseded | 预留状态，当前没有代码路径产生 | 否 |

`skipped` 与 `failed` 的区别是语义：`failed` 表示这次没成功、下次要重试；`skipped` 表示重复执行也不会有不同结果，因此计入已处理窗口并让锚点前进，避免每次运行都重复抽取同一段历史。`superseded` 目前不会有代码路径产生——批次签名由消息序列决定，窗口变化只会生成新签名的新批次，旧批次仍然有效；保留它是为了让状态机语义完整。

**conversation_qa_candidates**：从对话抽出的问答候选，是正式知识入库前的暂存记录。

| 字段 | 含义 |
| --- | --- |
| candidate_key | 唯一，由批次签名与候选在模型输出中的序号决定 |
| batch_id | 所属批次，外键级联删除 |
| conversation_id | 冗余保存的会话标识，便于不联表按会话统计 |
| question / answer / category | 已脱敏的真实问法、答案与分类 |
| source_user_message_id / source_answer_message_id | 来源消息标识，保证正式知识可追溯 |
| evidence / confidence | 模型给出的对话原文依据与置信度 |
| status | staged、promoted 或 rejected |
| rejection_reason | 不入库的原因，截断到 500 字符 |
| answer_fingerprint | 答案指纹，用于跨批次判断答案是否一致 |
| deduped_at / promoted_chunk_id | 去重处理时间，以及最终并入的 knowledge_chunks 主键 |

候选状态：`staged` 抽取后待去重处理；`promoted` 已作为正式知识写入 knowledge_chunks 并回填 `promoted_chunk_id`；`rejected` 不入库、`rejection_reason` 说明原因。被拒候选择保留在暂存表而不是删除，便于后续人工复核与调整抽取提示词。拒绝原因包括缺少必填字段、超出长度上限、答案过短或仍是提问、置信度过低、问法或答案依赖个人与交易标识、答案含糊或自相矛盾、答案在对话中没有明确依据、缺少分类、同一问法答案冲突，以及与已入库知识重复。

### 脱敏与个人数据边界

暂存表保存的是**已脱敏**的内容：手机号、地址、订单号、运单号、邮箱与证件号在调用模型之前就被替换成固定占位符（`[手机号]`、`[订单号]` 等）。正式知识只可能来自暂存表，因此正式知识同样不含这些信息。

替换用固定占位符而不是随机串，是为了让同一段对话每次都得到同一份文本，批次签名与候选指纹才稳定，重复运行不会因为脱敏结果抖动而产生新知识。

脱敏后仍带占位符的候选会被拒绝（问法或答案「依赖个人或交易标识」）：这类候选描述的是某个用户的订单状态或物流轨迹，把占位符当通用政策写进知识库会让检索返回残缺内容。

用户身份只用于理解对话上下文，不写入暂存表与知识库：暂存表只保存来源消息标识，不保存用户标识。

### 入库与幂等

去重与入库由 `app.services.rag.conversation_mining` 编排，判定规则与拒绝原因见 [`RAG.md`](RAG.md#整体去重)。数据层的关键点是入库仍走 `upsert_source_chunks`：

来源标识按**规范化问法集合**生成（`conversation-qa:<问法集合哈希>`），不是按会话或批次。理由是 `upsert_source_chunks` 的作废判定是「同一来源内本次未生成的块」：来源随问法集合走，同一组真实问法在每次运行中都映射到同一个来源，重复运行才不会把已经向量化的块置为 superseded。`chunk_index` 恒为 0，每个来源就是一条问答知识。

`ChunkUpsertResult` 为此增加了一个 `chunk_ids` 字段，把 chunk_key 映射到实际写入的 `knowledge_chunks` 主键，供候选回填 `promoted_chunk_id`，从而做到从知识反查抽取来源。文档与 FAQ 导入不使用该字段。

### 并发与续跑的数据层依据

并发靠「短事务认领」：在同一个事务里 `SELECT ... FOR UPDATE SKIP LOCKED` 后立刻把状态置为 `extracting`。行锁保证同一批次只会被一个运行拿到，`SKIP LOCKED` 让其他运行直接跳过被锁行而不是排队等待。进程级另有一把非阻塞文件锁，把同时启动的第二个任务实例挡在门外。

续跑靠状态：入口启动时默认先把上次被强杀留下的 `extracting` 批次放回 `pending`，再用批次签名与候选键跳过已完成的工作。数据库会话不跨模型调用持有——读消息、写候选、写状态各自是短事务，调模型期间没有任何打开的连接。

### 命令

命令位于 `backend/scripts/mine_conversation_knowledge.py`，都在 backend 目录下执行，连接与凭据来自 `backend/.env`。

    # 手动运行一次：抽取 -> 暂存 -> 整体去重 -> 入库 -> 补向量
    .\.venv\Scripts\python.exe -m scripts.mine_conversation_knowledge
    # 只抽取并写入暂存表，不做整体去重与入库
    .\.venv\Scripts\python.exe -m scripts.mine_conversation_knowledge --staging-only
    # 按周期常驻运行
    .\.venv\Scripts\python.exe -m scripts.mine_conversation_knowledge --interval 3600
    # 查看批次与候选状态统计，不写数据
    .\.venv\Scripts\python.exe -m scripts.mine_conversation_knowledge stats
    # 列出留待处理或已拒绝的候选及原因
    .\.venv\Scripts\python.exe -m scripts.mine_conversation_knowledge list-candidates --status rejected

定时循环是独立 CLI 进程，不在 FastAPI 导入阶段启动。仓库根目录 `start.ps1` 默认不运行挖掘，显式传入 `-EnableConversationMining` 才启动定时进程。员工控制台的鉴权 HTTP 接口可以触发一轮挖掘；它与 CLI 共用实例锁，只写候选和正式知识，向量补齐由独立任务触发。`extracted`、`ready` 中尚为 `staged` 的候选跨 `run_id` 汇总；只要全局还有 `pending`、`extracting` 或 `failed` 批次，整体去重暂缓。

## FastAPI 对话服务接入

- 登录、Cookie 会话、会话列表、消息历史、发消息和 LangGraph 上下文均使用 MySQL；服务启动不会自动建表或修改表结构。先运行 Alembic，再启动 API。
- LangGraph 按“识别意图、服务端选择工具、执行工具、依据结果保存最终回答”的流程运行。订单、物流、知识、售后申请、有效政策和工单状态均通过专用工具查询；`create_ticket` 只向既有工单表登记诉求，不创建退款申请或实时接入人工。具体契约见 [`tools.md`](tools.md)。
- `0002_chat_runtime` 是新增迁移，保留 `0001_initial` 不变。它增加登录会话表、消息重试键和会话预览字段。
- `0003_message_timestamp_precision` 将消息时间改为微秒精度，并修正已有用户消息与助手回复的成对顺序。
- `0004_knowledge_chunks` 新增知识块表，供离线建库使用；它不改动任何既有业务表。
- `0005_conversation_mining` 新增对话挖掘的批次进度表与问答暂存表，并把 `knowledge_chunks.content_type` 加宽到 VARCHAR(64)；它不改动任何既有业务表。
- 普通用户演示登录为 `maya@aiden.demo` / `chen@aiden.demo`，密码均为 `aiden123`。执行 `python -m scripts.init_demo_users` 可显式创建账号；它只补入不存在且无冲突的记录，不会重置已有密码。账号与目标库现有记录冲突时会停止并回滚。
