# 项目总结



## 介绍

Aiden是一个电商售后智能客服系统，用户可以在对话框中询问退换货政策，催物流，退款，由Aiden判断话的意图，走不同的流程

架构上使用 workflow + agent 的混合，让 llm 在强约束的业务里可靠地干活



## 面试题



### 流式输出怎么实现的？

模型流式生成 + LangGraph自定义事件 + HTTP SSE + React 增量渲染

后端在 generate 节点实际消费模型流，每收到一段正文，就通过自定义事件立即转成 SSE delta 发给前端。前端用 fetch 读取响应流、增量解析事件，把 delta 追加到消息中

我们区分草稿和最终答案：delta 是未核验草稿；引用核验并保存成功后，发送 final 替换正文和引用，再由 done 结束。如果核验失败，final 会把草稿替换成拒答，但已经展示的内容无法撤回。

另外，停止通过 AbortController 真正取消请求和生成；通过请求身份隔离、历史合并规则和 clientMessageId 幂等，避免轮询覆盖草稿、迟到内容重复追加，以及重试重复创建消息。



### Function Calling的原理？

模型本身不执行任何东西，它只会告诉你，它想调哪个工具，参数是什么，输出的是一个结构化的调用意图

比如Aiden系统中，定义了查订单，查物流这些工具，每个工具的名字，用处，参数都告诉模型，用户问[我的快递到哪了]，模型判断需要查物流，就吐出一个调用意图：工具名`query_logistics`，参数是订单号，记下来就是由外面的编排框架接管，参数校验，调物流接口，把结果回填给对话



### 完整讲一条RAG链路

离线建库方面，把知识文档按结构切成一个个片段，做向量化，原文也跟着一起存进向量库

在线问答方面，用户问题进来，先向量化，利用余弦相似度检索出最相关的几段，拼成一段带编号的证据注入 Prompt，模型严格按证据回答，关键结论后面标注来源编号

在检索和生成之间还有一道检查，看证据是否足够支撑回答，不够就拒绝回答



### 文档如何切分？

本项目的知识文档是`markdown`，所以采用结构感知切分

首先解析标题，简历章节树，然后在章节内以完整句子为最小单位，按token预算打包，相邻正文块留一定的完整句子重叠，减少上下文丢失

特殊内容单独处理：表格按行拆分并复制表头，代码块保持完整，超长句子，超宽表格行或超长代码块不强行阶段而是标记人工审核，暂不向量化

每块保留章节路径，分类等元数据，向量化时拼接“分类，问题，正文”，补充检索语境



### Embedding 模型怎么选的？维度是不是越大越好

从检索效果，业务适配和部署成本三个方面选择Embedding模型，而不是只看维度

* 检索效果：用真实业务问题和标注相关文档，对比 Recall@K，MRR，nDCG
* 业务适配：是否支持中文，领域术语，一如输入长度是否覆盖知识块
* 部署成本：评估推理延迟，吞吐，内存和显存，以及向量存储和索引成本

维度不是越大越好，高维不保证检索更准确，高维还会带来更高的存储，索引和检索开销，真正决定检索质量上限的是切分和检索策略

当前项目配置的是 BAAI/bge-small-zh-v1.5，输出512维，序列长度上限512tokens，中文轻量模型

### 为什么架构是 workflow 和 agent 混合？

客服有好几个环节要求高可靠性，不能全交给agent决定，否则它可能图省事跳过检索，凭记忆瞎答，该拒答的时候硬编

用 workflow + agent 混合，业务铁律用确定性流程写死，知识类先检索再答，退款先取证再判，投诉一律转人工，agent只在它擅长的开放推理环节发挥



### workflow + agent 混合架构具体是什么，为什么用 LangGraph？

具体就是一张状态图，把一个请求拆成一个个节点，意图识别，意图分流，检索，证据检查，主力agent，日志，节点之间用边连起来，一份共享状态贯穿全程
